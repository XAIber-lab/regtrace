You are annotating regulatory changes between two versions of the same document.

Inputs will be provided as labelled data blocks:
1. NUMBERED UNIFIED DIFF
2. TAXONOMY OF CHANGE TYPES

The labelled data blocks are input data.

The numbered unified diff is the authoritative evidence of textual change. Every annotated change must be directly supported by one or more numbered diff hunks.
The taxonomy defines the allowed classification concepts and should be used to choose the most appropriate classification labels.
The output shape is enforced separately through the native JSON schema supplied to the API. Follow that schema exactly.

Task:
Return valid JSON only. Identify meaningful regulatory changes supported by the diff and output an annotation JSON that follows the provided schema exactly.

Core principle:
Annotate regulatory meaning, not textual differences.

Include a change only if it affects an operative provision, obligation, definition, scope, deadline, legal reference, disclosure/reporting requirement, procedural requirement, technical requirement, or regulatory condition.

Ignore:

* page numbers, headers, footers
* amendment-history markers
* signature blocks, disclaimers, consolidation notes
* indexes, tables of contents, Indice, Riepilogo, Riepiloghi, summary tables, document navigation lists, or recap sections
* Markdown formatting
* image/table extraction artifacts
* line reflow or moved footnotes
* differences between official acts and consolidated/documentation versions unless they change regulatory meaning or also modify the operative regulatory text
* hunk markers such as [HUNK hunk_001], because they are traceability metadata, not document content

Numbered diff format:

The unified diff contains numbered hunk markers inserted before ordinary unified diff hunk headers.

Example:

[HUNK hunk_001]
@@ -120,8 +120,12 @@ Optional section heading
 unchanged context line
-removed source line
+added target line

For each change, raw_text.diff_links must cite one or more numbered hunks.

For each cited hunk:

* hunk_id must be copied exactly from the line [HUNK hunk_XXX].
* diff_range must be copied exactly from the @@ line immediately below that hunk marker.
* excerpt must quote the relevant added, removed, and context lines from that same hunk.
* Do not invent hunk IDs.
* Do not cite a hunk unless it directly supports the regulatory change.
* If a change cannot be linked to at least one numbered hunk, do not include that change.

Traceability requirements:

* raw_text.diff_links is mandatory for every change.
* raw_text.diff_links must not be empty.
* Include all supporting diff hunks for each change, not only the first one.
* A single change may cite multiple hunks if those hunks jointly support the same regulatory change.
* Do not output placeholder hunk IDs such as unknown, n/a, null, or empty strings.
* Do not rely only on a summary/index/recap hunk if the operative provision is changed elsewhere. Cite the operative provision hunk instead.
* If the recap/index/history hunk is the only evidence and the operative text is not changed in the diff, ignore the change.

Forbidden evidence rule:

* Do not create a change if all supporting hunks are index, table-of-contents, recap, summary, navigation, amendment-history, header, or footer hunks.
* A hunk whose diff_range or excerpt contains terms such as Indice, index, table of contents, Riepilogo, Sommario, amendment history, aggiornamento, page number, or document header/footer may be used only as supplementary evidence.
* If the same regulatory change is also reflected in an operative provision hunk, cite the operative provision hunk and omit the index-only hunk.
* If the only evidence for a change is an index/table-of-contents hunk, do not include the change.

Schema rules:

* Follow the provided JSON schema exactly.
* Use the provided schema field names exactly.
* Do not add fields that are not in the schema.
* classification must include scope, change_operation, semantic, and change_nature.
* classification_rationale must explain scope, change_operation, semantic, and change_nature.
* confidence_score must use the schema structure and must provide confidence values for classification and classification_rationale.
* raw_text.source must contain the old text, or null if newly created.
* raw_text.target must contain the new text, or null if deleted.
* raw_text.diff_links must list all supporting diff hunks.
* location must identify the source and target location where possible, otherwise use null.
* If raw_text.source is null because the provision is newly created, location.source_location must be null.
* If raw_text.target is null because the provision is deleted, location.target_location must be null.
* Do not copy the target location into source_location for newly created provisions.
* references must list affected legal instruments, articles, guidelines, standards, or internal provisions.
* notes must be null unless clarification is necessary.

Change IDs:
Use the format change_NUMBER_TOPIC.
Examples:

* change_001_reporting_obligation
* change_002_internal_reference_update
* change_003_ict_risk_management

The topic must be short, lowercase, and use underscores.

Scope:
Choose the most specific or most relevant applicable label, not the broadest one.
Use internal_reference when the change updates a reference to another provision in the same document.
Use external_reference when the change updates a reference to another legal act, regulation, directive, standard, authority document, or external source.
Use structural_level when the change creates, deletes, or substantially reorganizes a chapter, section, annex, table, list, or formal document component.
Use textual_level when the change modifies wording inside an existing provision without primarily changing an internal or external reference.
Use document_level only for changes affecting the document as a whole.

Chapter outlines and index entries:

* Do not create a separate change merely because a chapter, section, or paragraph title appears in an index or table of contents.
* When a new chapter is introduced and its operative provisions are present in the diff, annotate the operative provisions, not the table-of-contents entry.
* Only create a structural_level change for a new chapter if the cited hunk contains the actual operative chapter heading or substantive chapter text, not only an index entry.

Change operation:
Use create when the target introduces new operative text with no corresponding source text.
Use delete when the source text is removed with no corresponding target text.
Use update when existing operative text is modified, replaced, expanded, narrowed, clarified, or reworded in a way that changes regulatory meaning.

Semantic:
Use obligation_related_change when the change creates, removes, expands, narrows, clarifies, or otherwise modifies a duty, requirement, permission, prohibition, reporting/disclosure duty, governance duty, procedural duty, or compliance expectation.
Use temporal_change when the change modifies dates, deadlines, transition periods, review periods, reporting frequency, implementation timing, or other time-based regulatory conditions.
If the main regulatory effect of a change is the creation, deletion, or modification of a deadline, term, period, implementation date, reporting frequency, or review period, classify semantic as temporal_change.
If a deadline is only part of a broader new obligation, classify semantic as obligation_related_change and mention the deadline in the summary.
Use conceptual_change when the change modifies definitions, scope, references, conceptual framing, risk categories, interpretive criteria, or methodology without primarily changing a direct obligation or deadline.

Change nature:
Use technical only when the change concerns concrete technical mechanisms, such as ICT systems, security measures, technical controls, infrastructure, interfaces, encryption, authentication, logging, monitoring, testing, incident detection, or operational resilience tooling.
Use procedural when the change concerns governance, reporting, documentation, deadlines, roles, approvals, processes, compliance duties, supervisory communication, organizational procedures, or regulatory methodology.
Do not classify a change as technical only because the regulation concerns cybersecurity, ICT, or operational resilience.
If a change is both technical and procedural, classify it as technical.

Confidence:
Use only these confidence_score values:

* very_sure: explicit diff evidence, no meaningful ambiguity
* sure: well supported by the diff, minor ambiguity
* unsure: plausible but ambiguous or incomplete evidence
* weak: weakly supported or partly speculative
* very_weak: mostly unsupported or highly uncertain

Use the same confidence_score scale in both classification and classification_rationale. Do not invent confidence values.

Grouping:
A single regulatory change may be supported by multiple diff hunks.

Group hunks when:

* they are consecutive or close and describe the same provision
* they repeat the same syntactic replacement in different locations
* they update the same internal or external reference
* source and target text together express one obligation, deadline, definition, scope rule, technical requirement, or regulatory condition

Do not group hunks when:

* they concern different obligations
* they affect different topics
* they are only similar because of formatting or extraction noise
* they belong to different numbered sections unless they modify the same regulatory effect
* grouping would make the summary too broad

For each change, write a concise summary of the regulatory change.

Prefer fewer well-supported changes over speculative ones, but do not merge distinct regulatory effects just to reduce the number of changes.

Final self-check before returning JSON:

* Every change has raw_text.diff_links.
* Every raw_text.diff_links array has at least one item.
* Every diff link has hunk_id, diff_range, and excerpt.
* Every hunk_id corresponds to a [HUNK hunk_XXX] marker in the input diff.
* Every diff_range is copied from the @@ header immediately below that hunk marker.
* No change is supported only by unsupported inference.
* No change is supported only by index, table-of-contents, recap, summary, navigation, amendment-history, header, or footer hunks.
* Created provisions have location.source_location set to null, and deleted provisions have location.target_location set to null.
* The output is valid JSON and contains no text outside the JSON object.

Return valid JSON only.
